# 失败案例

> 数据来源：`experiments/run_failure_analysis.py` 与 `run_abstention_eval.py` 的实测输出（2026-10-19）
> 用法：面试被问「它什么时候会错」时，直接拿这几条讲——比讲指标更有说服力。

---

## 案例 1｜文档摘要类查询：块级召回结构性失效

**现象**：问「XX 制度怎么规定」这类问题时，返回的 top-3 全是**别的文档**的片段。

| 查询 | 标准答案（同文档 3 块） | 候选池中的名次 | 实际返回 top-5 |
|---|---|---|---|
| 培训与晋升制度怎么规定？ | d4_ch1 / d4_ch2 / d4_ch3 | 8 / 4 / 6 | d3_ch1, d9_ch1, d3_ch3, d4_ch2, d11_ch2 |
| 绩效与考勤补充规定了什么？ | d7_ch1 / d7_ch2 / d7_ch3 | 4 / 8 / 25 | d9_ch1, d3_ch1, d3_ch3, d7_ch1, d9_ch2 |
| 信息安全与保密制度的核心要求是什么？ | d10_ch1 / d10_ch2 / d10_ch3 | 6 / 20 / 9 | d8_ch2, d1_ch2, d9_ch1, d3_ch3, d3_ch1 |

**根因**（不是"召回没召回"，是"召回了但排不上"）：

1. 「XX 制度怎么规定」与**任何单一块**都只有中等相似度——它要的是一篇文档的整体；
2. 正确答案分散在同一文档的 3 个块里，块级召回最多命中其中 1 块；
3. 其他文档的块因为术语重叠（"制度""规定""员工"）反而得分更高：销售提成、年终奖、远程办公被顶上来。

**影响**：文档摘要类场景 recall@3 只有 **0.6667**（其他场景 0.95–1.0），是全链路最弱的一环。

**兜底 / 修复方向**：
- 文档级两级召回：先按 doc 聚合分数定位文档，再取该文档内 top chunks；
- 或命中某块后做**同文档邻块扩展**（把 ±1 块一并带回）；
- CE 重排能部分修复（hit@3 → 1.000），但 recall@3 仍停在 0.6667，说明是结构问题，不是排序问题。

## 案例 2｜l3 重排输出被截断（3/60）

**现象**：JSON 解析报 `Expecting value: line 1 column 708` / `Unterminated string starting at ... column 310`。

**根因**：l3 要求模型对 15 条候选逐条输出 `{id, score, reason}`，输出长度可达 1,000+ tokens；
而 `simple_query` 的 `max_tokens=2048` 被**推理 + 输出**共同消耗，输出中途被切断，JSON 不完整。

**影响**：该查询回退到 Cross-Encoder（结果不差），但**已经花掉的 1,537 token 白费**，
且用户侧延迟从 0.96s 涨到 5.8s。本次 60 条实测触发 **3 次**。

**兜底**：已有（回退 l2 → 再回退 l1），所以不会答错。
**修复方向**：把候选从 15 降到 8；或让模型只输出 `id:score` 不带 `reason`；或提高 `max_tokens` 到 4096。

## 案例 3｜l3 返回空内容（1/60）

**现象**：`content` 长度 0，`reasoning_content` 长度 3,291 字符 → `JSONDecodeError: Expecting value: line 1 column 1 (char 0)`。
触发查询：「OA 系统申请和 HR 注销权限分别在什么场景用？」（对比 + 场景判断型，思考链最长）。

**根因**：推理型模型把 2048 token 预算**全部花在 thinking 上**，正文一个字都没剩下。
这是"输出预算"问题，不是"模型不会输出 JSON"——干净样本、真实候选、754 字符提示词分别验证过，均正常。

**影响**：同案例 2，回退 CE，多花一次调用。
**修复方向**：检测空返回重试（并提示「不要输出思考，直接给 JSON」）；或重排用非推理模型。

> 值得注意：**同一个坑在项目里踩了两次**——l3 重排和评测 judge 各一次。
> 因此给评测 judge 加了「空返回自动重试 + 提高 max_tokens」，修完 40 条判定一致率从 85% 升到 100%。

## 案例 4｜「拒答但附参考」的边界

**现象**：20 条负样本中，3 条是纯拒答（只说"资料未规定"），**17 条是拒答 + 附上资料里其他相关条款**。

例如问「境外出差的补贴标准是多少？」，回答：
> 根据现有资料无法确定境外出差补贴。当前资料仅涉及境内出差规定——住宿每晚不超过 500 元、交通优先高铁二等座……**（不适用于境外）**

**为什么算风险**：回答里出现了具体数字（500 元），用户可能只扫到数字而忽略"不适用于境外"的限定。
判定上它不算编造（数字确实来自资料），但**产品上需要显式区分**。

**兜底**：当前靠措辞（"不适用于境外"）区分，不可靠。
**修复方向**：回答模板强制两段式——先给结论（资料未规定），再给"仅供参考的相关条款"，并加视觉分隔；
或对"拒答 + 附参考"单独计数，作为产品指标（当前 17/20）。

## 案例 5｜top-1 引错块（hit@1 = 0.9167）

**现象**：CE 重排后 hit@3 = 1.000，但 hit@1 只有 **0.9167**——5 条查询的 top-1 不是标准答案块。

**影响**：答案内容大概率仍正确（因为 top-3 里有正确答案），但**首条引用可能指向次优块**，
在"引用必须点回原文"的产品要求下，这是可见的瑕疵。

**根因**：同文档内的块高度相似（同一制度的不同条款），CE 分数接近，排序靠微小差异。
**修复方向**：候选去重时优先保留同文档首块；或输出时对同文档多块做合并展示。

## 这些失败怎么用

| 用法 | 话术 |
|---|---|
| 面试被问"它什么时候会错" | 先讲案例 1：整篇文档类查询会答偏，根因是块级召回的结构性缺陷 |
| 被问"你怎么保证不出错" | 讲案例 2/3 的降级链：l3 → l2 → l1，任何一档失败都不会答错，只是慢 |
| 被问"你怎么知道它没瞎编" | 讲案例 4：负样本 20 条，编造 0，但"附参考"的边界要单独管 |
| 被问"你踩过什么坑" | 讲"同一个 token 预算问题在项目里踩了两次，后来统一加了空返回重试" |
